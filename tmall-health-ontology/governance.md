# 试点期治理：角色分工与口径变更流程（governance）

> 行业试点不需要完整组织架构图。需要的是：每类材料有唯一负责人、
> 口径变更有流程、badcase 有回收渠道。就这三件事。

## 1. 角色与 RACI

试点期 4 个角色即可（可以一人兼多角）：

| 角色 | 谁 | 负责 |
|------|-----|------|
| 业务 owner | <行业小二，花名> | 指标口径**签字确认**、术语表审核、SOP 认可、试点范围圈定 |
| 数据 owner | <分析师/数仓，花名> | 指标口径起草、宽表建设与数据质量、维度字典 |
| 建设者 | <你，花名> | 本体定义起草、工具注册、agent 编排、评测集维护与回归 |
| 试点用户 | <3~5 名真实小二> | 贡献高频问题、日常使用、badcase 反馈 |

材料与负责人对照（R=起草 A=签字 C=咨询）：

| 材料 | 业务 owner | 数据 owner | 建设者 | 试点用户 |
|------|-----------|-----------|--------|---------|
| ontology.yaml | A | C | R | — |
| metrics.yaml / dimensions.yaml | A | R | C | — |
| glossary.md | R/A | — | C | 贡献 |
| tools.yaml | — | A | R | — |
| qa_evalset.yaml | C | C | R | 贡献 |
| sops.md | A | R | R | 贡献 |

## 2. 口径变更流程（核心流程，必须走）

```
提议（任何人）
  → 数据 owner 评审可行性与影响面
  → 业务 owner 确认业务含义
  → 修改定义文件，status: draft → confirmed
  → 建设者跑 qa_evalset 全量回归
  → 通过后发布，changelog 记一行（改了什么、为什么、影响哪些问题）
```

- 未走完流程的口径一律保持 `draft`，agent 使用时必须声明"口径未确认"。
- 紧急修错（口径写错了）也走此流程，只是加急，不跳步。

## 3. 运行节奏

- **每周 30 分钟评审会**：过一遍本周 badcase → 归类为「口径问题 / 术语没听懂 / 工具缺失 / SOP 缺失」→ 落到对应文件的 TODO。
- **badcase 收集渠道**：<钉钉群 / 表格链接>，试点用户随手丢原始对话截图即可，由建设者归档。
- **每两周**：评测集补充 5~10 条新 case（来自真实 badcase），保持评测集与真实使用同步。

## 4. 岗位要不要建成本体对象？

判断标准（满足任一才建）：

- 出现「这事该找谁 / 派单给XX」类问题
- 出现「按岗位定向推送」需求（如给每个商家运营推自己负责店铺的预警）
- 权限规则复杂到需要按"岗位-负责范围"数据化管理

试点期通常都不满足 → **不建对象**，只在 `tools.yaml` 的 permissions 里用用户组粗粒度控制。
未来要建时，对象骨架已在 `ontology.yaml` 末尾预留（role）。
